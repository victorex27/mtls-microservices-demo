# Vault: PKI-managed certificates + rotation

## Why Vault, and what it costs you

Running Vault for a 3-service demo is genuinely more infrastructure than
strictly necessary - it's effectively a 4th deployed service that itself
needs unsealing, its own storage backend, and its own access control. If
you just want to see mTLS work, `scripts/gen-local-certs.sh` (plain
openssl, documented in [LOCAL_TESTING.md](./LOCAL_TESTING.md)) gets there
in seconds with no Vault at all.

What Vault buys you, and the reason it's wired in here anyway:
- **No long-lived private keys on disk.** Certs are issued with a 24h TTL
  (`max_ttl=72h`) instead of the 365-day certs the openssl script makes.
- **Centralized revocation.** Compromise one service's key -> revoke its
  PKI role / AppRole, not "SSH into every box and rotate a shared file."
- **An actual audit trail** of every certificate ever issued (`vault audit`,
  not covered here but trivial to add).
- **A real rotation mechanism to point at**, instead of "SSH in and re-run
  openssl every 90 days."

## Two CAs, not one

There's a bootstrapping problem: Vault's own HTTPS listener needs a
certificate before Vault is unsealed and its PKI secrets engine is even
configured. So there are two independent trust roots in this repo, and
mixing them up is the most common setup mistake:

1. **`vault/tls/vault-ca.pem`** - a plain self-signed CA generated by
   `vault/scripts/gen-vault-listener-cert.sh`, used ONLY to secure Vault's
   own API/UI port (8200). You (the operator) trust this CA when you run
   `vault` CLI commands (`VAULT_CACERT=vault/tls/vault-ca.pem`).
2. **The `pki_int` intermediate CA inside Vault** - generated by
   `vault/scripts/setup-pki.sh`, this is the CA that signs `api-gateway`,
   `users-service`, and `orders-service` certs. This is the one the three
   NestJS apps trust (`TLS_CA_PATH`), and it has nothing to do with #1.

If `curl`/`vault` complains about cert verification talking to Vault
itself, you want CA #1. If a NestJS service complains about handshake
failures talking to a peer service, you want CA #2.

## The PKI hierarchy

```
pki/            Root CA (mtls-demo Root CA), 10yr TTL, only ever signs the
                 intermediate. Effectively "offline" after setup.
  └── pki_int/  Intermediate CA (mtls-demo Intermediate CA), 1yr TTL.
                 Does the actual day-to-day issuing.
       ├── role: gateway-role         (CN=api-gateway only)
       ├── role: users-service-role   (CN=users-service only)
       ├── role: orders-service-role  (CN=orders-service only)
       └── role: test-client-role     (CN=test-client, for scripts/test-mtls.sh)
```

Each role's `allowed_domains` locks it to exactly one CN - `gateway-role`
cannot be used to mint a `users-service` cert, even by someone holding the
gateway's AppRole credentials. See `vault/scripts/setup-pki.sh`.

## AppRoles: how each service authenticates to Vault

Vault needs to know "this specific Vault Agent is allowed to request an
`api-gateway` cert" without a human typing in a password. That's
[AppRole auth](https://developer.hashicorp.com/vault/docs/auth/approle):
each service gets a `role_id` (not secret, like a username) and a
`secret_id` (secret, like a password), generated by
`vault/scripts/setup-approles.sh` and written to
`vault/agent/creds/<service>/{role_id,secret_id}` (gitignored - regenerated
per-environment, never committed). The matching policy
(`vault/policies/<service>-policy.hcl`) grants that AppRole exactly one
capability: `create`/`update` on `pki_int/issue/<service>-role`. Nothing
else - it can't read other services' secrets, can't touch the CA config,
can't list other roles.

## Vault Agent: the piece that actually rotates certs

Each service has a **Vault Agent** sidecar container
(`vault/agent/<service>-agent.hcl`) that:

1. Authenticates via AppRole (auto-retries, re-authenticates before its
   token expires).
2. Renders a `template` block: `vault/agent/templates/<service>-bundle.json.tpl`
   calls `pki_int/issue/<service>-role` and dumps the *entire* response
   (`certificate`, `private_key`, `issuing_ca`, `expiration`, ...) as JSON
   to `/certs/bundle.json`.
3. Runs a `command` hook after every render:
   `vault/agent/split-bundle.sh`, which splits that JSON into
   `tls-cert.pem` / `tls-key.pem` / `ca-cert.pem` (the three files the app
   actually reads), writing via temp-file + atomic `mv` so the app never
   sees a half-written file.

**Why one JSON bundle instead of three separate templates** (one for cert,
one for key, one for CA): each `{{ with secret ... }}` block in a Vault
Agent template is its OWN API call to `pki_int/issue/...`, and every call
mints a **brand new keypair**. Three separate templates would produce a
cert/key pair that don't match. One template, one issuance, one consistent
bundle - then split it locally.

Vault Agent automatically re-renders (and thus re-issues) as the lease
approaches its TTL, so certs rotate every ~24h without anyone touching the
box. You can also force it immediately for testing: `scripts/rotate-certs.sh`.

## How a running app picks up a rotated cert

Node's HTTPS/gRPC servers don't hot-swap TLS credentials mid-process. Two
realistic options: (a) implement live credential reload in every service,
or (b) restart the process on rotation and let it re-read the files at
boot. This repo takes (b) - it's simpler, it's obviously correct (no
partial-reload edge cases), and a container restart is sub-second:

- `src/cert-watcher.ts` in each service uses `fs.watch()` on the three PEM
  files. On change (debounced 2s, since a single logical rewrite can fire
  multiple fs events), it calls `process.exit(99)`.
- Each Docker image's `entrypoint.sh` is a small loop: run `node dist/main.js`,
  and whatever the exit code, restart it after a 1s backoff. dokku/docker's
  own restart policy is the outer safety net if the loop itself dies.

The trade-off: a live connection through a service being restarted for
rotation gets dropped, and callers see a brief connection error. For a
demo this is fine and arguably a feature (it proves rotation happened). In
a system carrying real traffic, you'd want (a) hot-reload, or at minimum a
graceful drain before restart - noted as future work below.

## Unsealing and the root token

`vault/scripts/init-vault.sh` runs `vault operator init` with 5 key shares
and a threshold of 3 (Shamir's Secret Sharing), then unseals with 3 of
them and writes everything to `vault/secrets/vault-init.json` (gitignored,
`chmod 600`). That's fine for a demo/single-operator setup. It is **not**
fine for a real production Vault: in that world, the 5 key shares go to 5
different people, none of whom can unseal Vault alone, and the root token
is used once to bootstrap other auth methods and then revoked
(`vault token revoke <root token>`). See HashiCorp's own
[production hardening guide](https://developer.hashicorp.com/vault/tutorials/operations/production-hardening)
for the full checklist (auto-unseal via a cloud KMS, non-root admin
policies, audit logging, etc.) if you take this further.

## Future work (deliberately out of scope here)

- **Hot-reload instead of restart-on-rotation** - e.g. re-creating the
  gRPC server's credentials object and swapping it on the existing
  listener, or a proxy sidecar (Envoy) doing TLS termination so the
  Node process never touches certs directly.
- **Vault auto-unseal** via AWS KMS, so a reboot doesn't require manually
  running `init-vault.sh`'s unseal step again.
- **Multi-node Raft cluster** for Vault itself, instead of the single node
  this demo runs (fine for one EC2 instance, not fine for real HA).
- **Client retries with backoff** in the gRPC clients (`users.client.ts`,
  `orders.client.ts`) so a rotation-triggered restart of a downstream
  service doesn't surface as a user-visible error at all.
